# 归并前的评分与决策标尺（先定尺子，再看数据）

> 目的：防止"star 最高的赢"这种懒惰结论。所有候选方案必须过下面两把尺子。

## 尺子一：需求匹配度（R1–R6 加权）

| 代号 | 需求 | 权重 | 判定标准（怎样算满分） |
|---|---|---|---|
| R1 | 桌面玩 MC | 1 | 玩家自己在 Windows 上有正常可玩的 MC（原版客户端） |
| R2 | AI 一起玩 | **3** | **同服同世界**、AI 能感知玩家行为并协作（不是"AI 自己玩你看"） |
| R3 | 轻量化 | **2** | ≤3 步部署、无需 GPU、无需改客户端、有现成发行物 |
| R4 | 手机"看到" | 2 | 手机零安装（浏览器）看到 AI 视角 + 能与 AI 说话 |
| R5 | 手机↔电脑互联 | 1 | 局域网零配置可通；公网可选 |
| R6 | 手机端 DSH | 1 | 能明确回答"要不要在手机上跑 agent"（结论可以是"不要"） |

**特别提醒**：R2 权重最高，因为它是用户这句话的主语（"让 AI **一起**玩"）。任何"AI 自己玩、你旁观"的方案，R2 直接判 1 分而不是 3 分。

## 尺子二：工程可行性（每项 0–2 分）

1. **成熟度**：star + commit 频率 + issue 响应 + release + 是否 npm 发布（不只看 star）
2. **可维护性**：license 是否清晰、语言/栈是否主流、依赖是否腐化（周边插件 2 年没更新要扣分）
3. **可集成性**：能否被 DSH 驱动（MCP tool / plugin / CLI）、接口是否稳定
4. **失败模式**：装不上、版本绑定、要正版账号、要公网、要 root —— 有几条扣几分
5. **中文可用性**：中文文档/社区、国内网络可达（HF 镜像、npm 镜像、豆包/DeepSeek 而非 OpenAI）

## 决策点（最终要你拍板的 3 件事）

- **D1｜"一起玩"的形态**：A) AI 自己玩你旁观（现成，dsh-game 就是这个） B) AI 与你同服协作（要自己做） C) AI 只是语音陪聊+偶尔帮忙（最轻）
- **D2｜"手机看到"的形态**：A) 手机浏览器开 DSH（零安装，看的是 DSH 界面 + 摄像机窗口串流） B) 手机串流整个屏幕（Sunshine/Moonlight） C) 手机摄像头拍屏幕（最直觉、最脆）
- **D3｜AI 大脑**：A) DSH 当大脑（MCP/插件） B) 自己写 Node 循环直连 LLM C) 用现成项目（mindcraft）改

## 反直觉的先验判断（供对照，不许直接照抄成结论）

1. **"手机摄像头看到"大概率是伪需求**：用户想要的其实是"我在床上也能看到 AI 在玩、还能跟它说话"。摄像头拍屏幕是手段错位；`dsh web --host` + token URL 已经解决 90%。
2. **"手机端跑 DSH"应当被否掉**：DSH 是 agent 宿主，跑在 PC 上才合理；手机只该当"屏 + 麦克风 + 喇叭"。
3. **"AI 一起玩"的技术核心不是模型，是"感知 + 目标同步"**：mineflayer 的观察是结构化状态，缺的是"玩家在干什么"的语义（玩家在挖矿？在建房？在逃跑？）。
4. **最容易被忽略的成本是 MC 版本与离线服务器**：dsh-game 只在 1.21.4 测过、必须 `online-mode=false`，这一条会劝退一半用户。
