# 独立审核结论与方案修订记录

> 审核日期：2026-11-16（Asia/Shanghai）
> 审核范围：产品/交接文档、AR/同步/AI 架构、素材许可与发布风险、现有 M0 预览。
> 结果：用户已明确确认 AR 产品方向及 v0 边界；修订版见 [IMPLEMENTATION-PLAN.md](IMPLEMENTATION-PLAN.md)。这是工程审核，不构成正式法律意见。

## 1. 用户确认的产品定义

用户明确要求：**默认需求是在物理桌面上看到大肥鱼（AI）建设方块世界，并且玩家可以参与建设。** 会话中进一步确认：

- 产品形态为真实桌面微缩沙盒，不是 MC 屏幕投影。
- Android 支持 ARCore 的设备/WebXR 真 AR 优先。
- v0 为单个 3D 大肥鱼角色；独立 Windows 桌宠窗暂不要求。

因此，先前“产品方向是否转向 AR”这一阻断已由用户回答，不再作为待确认项。用户确认 AR **不等同于**确认某个 SDK、许可、延迟、设备覆盖或既有实现已可用。真实 Minecraft 联动也不在当前确认的 v0 范围内。

## 2. 审核结论摘要

- `preview/` 只证明可在当前 PC 环境渲染静态体素画面、展示 three.js 示例 GLB 并生成截图；它没有证明真机 AR、触控建造、同步、持久化、AI 仲裁、DSH 工具或移动性能。
- 既有 `PLAN.md`、`REPORT.md`、`docs/DEV.md` 和 E/F/H/I/J 子报告之间存在多个不同方案及互相冲突的字段。现在由 `IMPLEMENTATION-PLAN.md` 提供统一建议，但共享 schema、协议、代码和自动测试尚未落地。
- 技术方向总体可做；真正先验风险是 Android HTTPS/WSS 配对、WebXR 真机锚定与透明渲染、事务/重连语义、资产权利链和未建立的构建/测试入口。
- 所有尚未真机验证的 AR 支持、性能、网络时延、模型规格和工作量都必须标成建议或待验证，不得写成已测事实。

## 3. 发现的问题与处理

### P0：开工前/发布前阻断

1. **历史文档将拟议规格写成已定接口。** `docs/DEV.md` 将 14×14×10、16×12×16、32×16×32 等多个世界域与不同消息协议并存；当前无共享协议实现。处理：新实施计划提出单一 `WorldSpec`/revision/事务建议；编码前仍须由技术负责人写 schema 和 ADR，并让测试通过，计划文字本身不能替代实现。
2. **同步 ACK、delta、revision 和 AI 批量仲裁没有可靠闭环。** 旧报告伪代码可能漏应用/重复应用 revision，计划与提交间有 TOCTOU，批量全原子与逐格跳过语义冲突。处理：新方案定义一 rev 一事务、clientId+seq 幂等、ACK 不推进 replica、计划 baseRev/hash/TTL、commit 重校验和原子拒绝；要求双客户端竞态与乱序测试。
3. **HTTPS 与 LAN WSS/凭证部署不闭环。** 旧文档给 `ws://` 与 query token 示例，同时相机/WebXR 需要安全上下文。处理：新方案要求同源 HTTPS/WSS、短期一次性凭证、loopback-only MCP、不得 query token；M0 先实机验证本地配对/TLS/防火墙步骤，不承诺零配置。
4. **AI 修改玩家世界的安全约束不足。** 上游图纸/执行代码可能包含清除语义；读取玩家文本或世界内容有 prompt-injection 风险。处理：限材料 allowlist、schema 化 DSL、禁止 eval/Lua/RCON、默认只放空格、用户确认后原子 commit、undo 条件检查；以负向测试为门禁。
5. **素材权利证据不足。** 公开仓库已含带水印效果图及蓝色小肥鱼模型渲染截图；README 的“仅作参考/非 MIT”或署名本身不等于公开分发授权。BlueFatFish 元模型禁止再分发；DeepSeek-chan/dsh-game 资产有 NC-SA 与署名/衍生条件；角色、动画、截图与商标链需逐文件核实。处理：发行版对 unknown/NC/未批准素材 fail closed；发布前取得效果图、模型截图及包含占位模型的 M0 截图的公开分发权或从公开/发行内容中排除，并清查现存副本；正式角色授权单独过门。
6. **数据流与隐私说明缺失。** 摄像头帧、聊天、建造动作、DSH 日志、用户模型、网络传输可能跨设备或发往用户配置的模型提供方。处理：v0 默认相机帧仅客户端处理、无长期 journal；实施前形成数据流图和告知，定义日志、保留、删除、备份、用户模型导入/传输与外部 LLM 边界。
7. **当前工程命令/测试不可交接。** 根工作区无正式 package/workspaces；审核时 `preview/package.json` 的 test 脚本固定失败，已改为 `check` 语法检查和 `smoke` 截图命令，但这仍不是功能测试，文档中其他 build/test/bench 命令也未创建。处理：M1 建立 fresh-clone 可复现安装、构建、测试与 CI；之前不要声称全栈骨架已可跑。

### P1：实现前验证/质量风险

1. **AR 能力被混写。** `photo` 3DOF 不是桌面固定 6DOF anchor；WebXR 合成相机背景通常不可由页面做整屏移轴。旧文档把 photo 当“真 AR 保底”，并对不同 provider 用同一个视觉验收。处理：M0 先 Android WebXR；将 tracking lost/恢复显式建模；photo 仅作降级展示，不算真 AR，通过 provider capability 分档验收。
2. **iOS/8th Wall 结论冲突。** 报告对 SLAM binary 的能力、许可、商业使用说法互不一致。处理：iOS 不进 v0；SDK/binary 固定版本、许可原文和设备 POC 全部核准前，不承诺 iOS 真 AR。
3. **真机性能和尺寸预算不是 M0 实测。** PC headless/SwiftShader 截图不能代表 Android GPU、热态、相机合成或 VRM 效能。处理：指定低/中档 Android，记录 10 分钟 p50/p95 帧时间、热状态、内存和锚漂移；实测后调整预算。
4. **估时过于乐观且跨报告不一致。** 2 周计划与各子报告的人日估算冲突，且未含 TLS、许可、存档、真机回归。处理：不保留日历保证；先做 M0 风险 spike，再依实际模块负责人和速度排期。
5. **运行时持久化承诺没有 RPO 口径。** 周期快照不能自动保证已 ACK 操作可在断电后恢复。处理：实施计划建议 ACK 前 durable WAL flush + 原子快照，测试截断和损坏恢复；实际若选择较弱保证，产品须明确允许丢失窗口。
6. **角色身高/预算/动画表分叉。** 旧 DEV 与 I/J 报告对身高、材质/文件预算、动画枚举意见不同，且示例模型许可或动画未必满足发行。处理：以最终有权模型实测，统一 manifest schema；占位模型和 PC 截图不作为移动发行性能证明。

### P2：文档与协作问题

- `PLAN.md` 的桌面 MC 调研问题与当前 AR 确认范围不同；留作历史调查，不应驱动 v0 产品实现。
- 报告中“已有项目验证 PNG 图片预览”“2 周能完成”等表述应基于具体源码/可重复步骤复核；功能借鉴不等于依赖可直接复用。
- `preview` package 起初标记 ISC，与仓库根许可说明不一致；本次已将 package.json 和 lockfile 根包元数据改为 MIT。应在后续 license scan 中再次核对仓库代码范围与各依赖的独立许可证。
- `refsrc/` 被忽略，不应是唯一上游源码来源；复用代码需固定 commit/hash、保留许可 notice。
- 文档中的 star 数、设备支持、服务条款、下载量都是带采样日的调查材料，时效性不等于当前发行事实。

## 4. 修订后的实施顺序

按依赖排列为：M0 Android 真机 AR/TLS/WSS spike → M1 正式 workspace + schema → M2 体素核心与渲染 → M3 worldd/事务/存档 → M4 AR 触控建造 → M5 DSH 预览确认共建与角色 → M6 资产清理、性能和发布候选。模块责任、接口建议及验收矩阵详见 [IMPLEMENTATION-PLAN.md](IMPLEMENTATION-PLAN.md)。

发布阻断：发布资产权利链、隐私数据流/外部 LLM 告知、安全凭证、存档恢复、许可证扫描、构建/测试/升级/回滚流程均须有可复现证据。

## 5. 证据边界

此审核以工作区当前材料及独立只读代码/方案审查为依据，未进行真实 Android/iOS 设备实验、SLAM SDK 集成、网络压力测试、正式法律意见或发行包审查。新增实施计划中的所有数值门槛都是建议验收目标，不是声称已有成绩。现有 M0 原型仍可用于静态渲染参考，但其随机纹理、PC 固定 Chrome 截图脚本和非正式 package test 不能作为跨平台 CI/性能验收。
